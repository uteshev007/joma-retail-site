# JOMA Retail — Telegram-боты аналитики продаж
## Техническое задание для реализации (Claude Code)

---

## 1. Цель

Два отдельных Telegram-бота на общей базе данных:

1. **Бот-аналитик** (закрытый, только владелец) — отчёты, алерты, приём файлов X2POS, сравнение цен конкурентов
2. **Бот-приёмщик сигналов** (для рабочего телефона продавцов в магазине) — приём свободных текстовых сообщений о том, что спросили, но не было в наличии

Хостинг — существующий ps.kz (PHP-only). БД — SQLite (общий файл для обоих ботов). Без сайта, без Mini App на первом этапе (можно добавить позже отдельным проектом).

---

## 2. Источники данных

### 2.1 Kaspi Магазин API
- `guide.kaspi.kz/partner/ru/shop/api`, эндпоинт `GET https://kaspi.kz/shop/api/v2/orders`, заголовок `X-Auth-Token`
- Токен уже получен владельцем — хранить только в конфиге вне публичной папки (см. раздел 7)
- Даёт: заказы, состав, статус, город/адрес доставки (география спроса), возвраты/отмены (косвенный сигнал по размеру/качеству)

### 2.2 X2POS — приём файлов через Telegram (без API, вручную загружает владелец)
Подтверждённые типы выгрузки, все — в бот-аналитик как документ, без отдельной команды (бот определяет тип по структуре колонок):
- **Номенклатура товаров** — справочник (категория, бренд, атрибуты) → таблица `products`
- **Прайс-лист** — цены, желательно себестоимость → расчёт реальной маржи
- **Продажи** — основа ABC/XYZ, тренда, прогноза стока
- **Контрагенты** — покупатели (если есть телефон/привязка к чеку) → таблица `customers`, база для анализа оттока и LTV
- **Платежи** — нал/карта → сверка с эквайринг-комиссией Halyk (отдельная тема проекта), не первый приоритет

**Переиспользовать из существующих систем проекта:**
- `catalog.json` из КП-генератора (`joma-kp-generator`) — готовый стартовый импорт номенклатуры (~1233 позиции с фото), не парсить с нуля
- Функцию `norm_article()` из КП-генератора — та же нормализация артикулов X2POS (float с обрезанными нулями)
- Архитектурный паттерн PHP-вебхука + вызов Claude API (Haiku 4.5) из уже работающего WhatsApp-бота — переносится на Telegram Bot API почти один в один

### 2.3 Демо-сигналы от продавцов (бот-приёмщик)
Свободный текст, без меню и без привязки к конкретному продавцу (атрибуция автора не нужна — важен только факт):
```
Продавец: 42 нет winner iv
Бот: 👍
```
AI (Claude API) разбирает текст, ищет соответствие в `products`, пишет в `demand_signals`. Никакого запроса имени/логина.

### 2.4 Цены конкурентов — без автоматического сопоставления
- **Kaspi** — если товар конкурента представлен на той же карточке Kaspi (несколько продавцов одного товара) — сравнение цены уже встроено в саму карточку, матчинг не нужен
- **chempion.kz, joma.kz/jomasports.kz** — ручная карта соответствий на ~10-20 топовых моделей (Winner IV, Phoenix III, Academy IV и т.д. — уже используются в B2B-пакетах): один раз владелец фиксирует пары «наш артикул ↔ ссылка на карточку конкурента», дальше бот только отслеживает изменение цены по сохранённой ссылке
- Instagram-магазины (@joma.kazakhstan и т.д.) — вне автоматики, ручная проверка как сейчас
- Частота проверки — раз в неделю

## 3. Схема БД (SQLite, общая для обоих ботов)

```sql
CREATE TABLE products (
    article TEXT PRIMARY KEY,
    name TEXT,
    category TEXT,              -- running/football/futsal/gym/barefoot/аксессуары
    brand TEXT DEFAULT 'JOMA',
    cost_price REAL,
    photo_path TEXT,             -- из catalog.json КП-генератора
    updated_at TEXT
);

CREATE TABLE stock (
    article TEXT,
    size TEXT,
    qty_on_hand INTEGER,
    updated_at TEXT,
    PRIMARY KEY (article, size)
);

CREATE TABLE sales (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    article TEXT,
    size TEXT,
    qty INTEGER,
    price REAL,
    sale_date TEXT,
    channel TEXT,                -- 'retail' | 'kaspi'
    kaspi_order_id TEXT,
    kaspi_city TEXT,
    customer_id INTEGER,         -- NULL если не определён
    seller_id TEXT,               -- логин продавца из X2POS (для эффективности, НЕ из Telegram)
    payment_method TEXT,          -- нал/карта, из выгрузки платежей
    source_file TEXT,
    imported_at TEXT
);

CREATE TABLE customers (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    x2pos_contragent_id TEXT,
    phone TEXT,
    name TEXT,
    first_purchase_at TEXT,
    last_purchase_at TEXT,
    avg_purchase_interval_days REAL,  -- пересчитывается при импорте
    ltv REAL                           -- сумма всех покупок
);

CREATE TABLE demand_signals (               -- от бота-приёмщика
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    raw_text TEXT,
    matched_article TEXT,
    matched_size TEXT,
    ai_confidence REAL,
    created_at TEXT
);

CREATE TABLE alerts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    alert_type TEXT,              -- 'size_deficit' | 'margin_drop' | 'churn' | 'competitor_price'
    entity_key TEXT,               -- article, article+size, customer_id и т.д.
    first_triggered_at TEXT,
    last_notified_at TEXT,
    resolved_at TEXT
);

CREATE TABLE competitor_prices (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    our_article TEXT,
    competitor TEXT,               -- 'kaspi' | 'chempion' | 'joma_kz'
    competitor_url TEXT,
    competitor_price REAL,
    checked_at TEXT
);

CREATE TABLE sync_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    source TEXT,                   -- 'kaspi' | 'x2pos_file' | 'competitor_prices'
    status TEXT,
    details TEXT,
    synced_at TEXT
);
```

## 4. Бот-аналитик (владелец) — функционал

### Команды
| Команда | Описание |
|---|---|
| `/start` | Справка |
| `/обновить` | Ручной запуск подтяжки данных из Kaspi API |
| *(отправка файла)* | Импорт X2POS-выгрузки (номенклатура/прайс/продажи/контрагенты/платежи — тип определяется по структуре) |
| `/отчёт` | Сводный дайджест: хиты, аутсайдеры, топ дефицитов, риски по стоку |
| `/хиты` `/аутсайдеры` | ABC/XYZ-анализ за период (инлайн-кнопки периода: 7/30/90 дней) |
| `/размеры [артикул]` | Размерная матрица — по товару или сводка по всем с перекосом |
| `/сток` | Прогноз дней до обнуления, рекомендации по дозаказу |
| `/тренд` | График по неделям/месяцам и категориям (картинка через QuickChart.io) |
| `/маржа` | Маржинальность по товару/категории, с историей относительно базовой линии |
| `/клиенты` | Топ по LTV, список «пропавших» (раз в месяц пересчитывается) |
| `/связки` | Топ пар товаров, которые чаще всего покупают вместе |
| `/цены_конкурентов` | Сравнение с сохранёнными карточками/ссылками конкурентов |

### Проактивные алерты (без команды, бот пишет сам)
Дедупликация через таблицу `alerts` — не слать одно и то же повторно, пока проблема не `resolved_at`. Группировка в дайджест, кроме самых срочных (дефицит размера у топ-товара — моментальный пуш).

| Тип | Частота проверки | Порог |
|---|---|---|
| Дефицит размера | При каждой синхронизации (после `/обновить` или импорта файла) | Прогноз «дней до нуля» < ~20-22 дня (15 дней произв./доставка + запас 5-7 дней); отдельный срочный алерт — остаток уже 0, а другие размеры того же артикула продолжают продаваться |
| Просадка маржи | Раз в неделю | Относительное падение >10-15% от скользящей средней категории за 6-8 недель |
| Отток клиента | Раз в месяц | 1.5-2× от индивидуального среднего интервала между покупками клиента (не общий порог для всех) |
| Изменение цены конкурента | Раз в неделю | Конкурент дешевле нашей цены больше чем на X% (порог откалибровать по факту первых данных) |

## 5. Бот-приёмщик сигналов (продавцы, общий рабочий телефон) — функционал

Единственная задача: принять свободный текст → распознать артикул/размер через Claude API → записать в `demand_signals` → ответить 👍.
Без команд, без меню, без запроса имени/логина продавца — эффективность конкретных сотрудников считается отдельно из X2POS (`seller_id` в `sales`, из выгрузки продаж), а не из Telegram.

## 6. Аналитические модули — логика расчёта

- **ABC/XYZ**: ABC по накопленной выручке (A — первые 80%, B — следующие 15%, C — остальное 5%), XYZ по коэффициенту вариации продаж по неделям
- **Размерная матрица**: % продано от поступления по каждому размеру артикула, перекос → сигнал на перекос закупки в пользу дефицитного размера
- **Тренд/сезонность**: группировка по неделям/месяцам и категориям (running/football/futsal/gym/barefoot); устойчивая сезонность проявится не раньше чем через ~год истории — помесячный тренд показывать с первого дня, сезонные выводы делать после накопления данных
- **Прогноз стока**: `скорость = продано за N недель / N`; `дней_до_нуля = остаток / (скорость/7)`; тот же механизм, что и дефицит размера, только на уровне артикула целиком
- **Связанные покупки (market basket)**: частота совместной встречаемости товаров в одном чеке — топ пар для допродажи
- **Скорость ответа на B2B-лид → конверсия**: логировать время первого ответа в WhatsApp-боте (уже есть история переписки), сопоставлять с итоговой продажей — отдельная метрика, не блокирует остальную разработку, реализуется по данным WhatsApp-бота, не Telegram
- **Аудитория**: география — из Kaspi (город доставки); время/день пиковых продаж, средний чек — из X2POS; демография (пол/возраст) не покрывается ни одним источником — отдельная тема (программа лояльности, уже в горизонте проекта)

## 7. Безопасность

- Kaspi API-токен и любые будущие ключи X2POS — только в `config.php` вне `public_html`, либо с `.htaccess` (`Deny from all`) на папку конфига
- SQLite-файл БД — вне публичной директории или с запретом скачивания `.sqlite`
- Бот-аналитик отвечает только владельцу — whitelist по `chat_id`
- Бот-приёмщик — открыт для рабочего телефона магазина, но не даёт доступа ни к каким командам аналитики (сам код не содержит такой логики — разделение на уровне архитектуры, не проверки внутри одного бота)
- Один бот может отправлять уведомления от имени другого через Telegram Bot API (`POST` с токеном нужного бота на `chat_id` владельца) — для срочных случаев, например когда сигнал от продавца пришёл по товару из топ-10 хитов

## 8. Развёртывание на ps.kz

1. Создать двух ботов через @BotFather → два токена
2. Разместить `/tg-bot-owner/webhook.php` и `/tg-bot-sellers/webhook.php` на joma-retail.kz
3. `setWebhook` для каждого на свой адрес (SSL на домене уже есть)
4. Проверить поддержку `pdo_sqlite` в PHP на ps.kz
5. cron — если доступен на тарифе, автообновление Kaspi раз в день; если нет — только по `/обновить`

## 9. Этапы реализации (по порядку)

1. Каркас бота-аналитика: вебхук, whitelist по chat_id, `/start`
2. Каркас бота-приёмщика: вебхук, приём текста, AI-распознавание, запись в `demand_signals`, ответ 👍
3. БД: создание SQLite и всех таблиц из раздела 3
4. Импорт стартовых данных: `catalog.json` из КП-генератора → `products`
5. Kaspi-интеграция: `KaspiClient`, `/обновить`, запись в `sales`+`customers`(частично)+`sync_log`
6. X2POS-импорт: приём файла, определение типа по колонкам, парсинг (переиспользовать `norm_article()`), запись в соответствующие таблицы
7. Аналитика базовая: `/хиты`, `/аутсайдеры`, `/размеры`, `/сток`
8. Алерты: таблица `alerts`, логика дедупликации/дайджеста, размер-дефицит + сток
9. Маржа и отток клиента: `/маржа`, `/клиенты`, алерты по обоим (с порогами из раздела 4)
10. Тренд/сезонность: `/тренд` с графиком через QuickChart.io
11. Связанные покупки: `/связки`
12. Цены конкурентов: ручная карта соответствий (интерфейс добавления пары «артикул ↔ ссылка»), `/цены_конкурентов`, еженедельная проверка
13. Сводный `/отчёт`, полировка форматирования всех сообщений
