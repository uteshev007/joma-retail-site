# JOMA Retail — sales bots

Два Telegram-бота на общей SQLite-базе. См. `JOMA_sales_bots_spec.md` (ТЗ) за полным контекстом.

## Структура

- `tg-bot-owner/webhook.php` — бот-аналитик (закрыт whitelist'ом по `OWNER_CHAT_IDS`)
- `tg-bot-sellers/webhook.php` — бот-приёмщик сигналов от продавцов (открыт всем)
- `db/schema.sql`, `db/init.php` — схема и инициализация SQLite
- `shared/` — общий код: конфиг, БД, Telegram API, Claude API, импорт X2POS, отчёты
- `scripts/import_x2pos.php` — ручной запуск импорта файла без Telegram (для теста)

## Локальный запуск

```bash
cp shared/config.example.php shared/config.php   # заполнить реальными токенами
php db/init.php                                   # создать SQLite-схему (необязательно — get_db() делает это сама)
php scripts/import_x2pos.php путь/к/выгрузке.xlsx  # тест импорта номенклатуры
```

## Деплой на ps.kz

Этот проект живёт в подпапке `tg-sales-bot/` репозитория `joma-retail-site`
(того же, что и лендинг) — деплой автоматический при пуше в `main`, тем же
механизмом, что и у сайта.

**Что деплоится само:** весь код при пуше в `main`.

**Что нужно сделать вручную на сервере после первого деплоя** (через файловый
менеджер ps.kz или SFTP — секреты через git не передаются):

1. Скопировать `shared/config.example.php` → `shared/config.php` прямо на
   сервере и заполнить реальными значениями (токены ботов, `OWNER_CHAT_IDS`,
   Kaspi/Claude/X2POS API ключи — `X2POS_API_LOGIN`/`X2POS_API_PASSWORD`, та
   же почта/пароль, что от личного кабинета x2pos.com). `.htaccess` в папке
   `shared/` уже блокирует прямой доступ по URL — но сам файл создаётся не
   через git.
2. Проверить, что PHP на хостинге поддерживает `pdo_sqlite`, `zip`,
   `simplexml` (раздел 10 ТЗ, не было подтверждено) — без них бот упадёт.
3. Зарегистрировать вебхуки в Telegram (заменить токены и домен):
   ```
   https://api.telegram.org/bot<ТОКЕН_ВЛАДЕЛЬЦА>/setWebhook?url=https://joma-retail.kz/tg-sales-bot/tg-bot-owner/webhook.php
   https://api.telegram.org/bot<ТОКЕН_ПРОДАВЦОВ>/setWebhook?url=https://joma-retail.kz/tg-sales-bot/tg-bot-sellers/webhook.php
   ```
4. Проверить `/start` в боте-аналитике — если `shared/config.php` на месте и
   расширения PHP есть, база создастся сама при первом запросе.
5. Загрузить актуальные выгрузки X2POS через бота (отправкой файла) — на
   сервере они запускают тот же импорт, что и `scripts/import_x2pos.php`
   локально.

`db/joma_sales.sqlite` и `photos/` создаются на сервере при первом
использовании — их не нужно (и не следует) коммитить в git.

## Статус реализации (относительно ТЗ)

Готово:
- Схема БД (раздел 3) + таблица `payments` (добавлена сверх ТЗ — см. ниже)
- Оба вебхука-скелета, whitelist владельца, `/start`
- Автоопределение типа X2POS-выгрузки по строке заголовков (заголовок ищется в первых
  15 строках — не всегда первая строка, экспорты начинаются со служебных строк вида
  «Компания:», «Период:»)
- Импорт **номенклатуры** — распознавание float-артикулов и восстановление артикула
  из «Кода товара» при браке в колонке «Артикул»
- Импорт **платежей** — как есть, upsert по «# платежа» (идемпотентно)
- Импорт **контрагентов** → `customers`, поставщики (`Признак поставщика = да`) пропускаются
- Импорт **продаж (чеки)** → `sales_documents` — итог чека, скидка, контрагент,
  без состава товаров (см. оговорку ниже)
- Импорт **продаж по товарам** → `sales` — построчно: артикул, размер (парсится из
  скобок в названии товара), qty, цена, себестоимость и маржа как в X2POS (не
  пересчитываются из `products.cost_price`, который может быть устаревшим),
  привязка к покупателю по телефону, номер чека для анализа связок
- Пересчёт `customers.ltv`/`first_purchase_at`/`last_purchase_at`/`avg_purchase_interval_days`
  по привязке чека к клиенту через телефон
- Импорт **прайс-листа** → обновляет `products.retail_price`/`discount_price` (не
  трогает `name`/`category`/`cost_price` у существующих товаров — те авторитетны
  из номенклатуры). Файл группирует товары строками-заголовками категорий вперемешку
  со строками товаров — распарсено с учётом этой структуры
- **Фото товаров** из прайс-листа (если в нём есть вклеенные картинки — не в
  ячейках, а через `xl/drawings/`) → извлекаются в `photos/` (в `.gitignore`, не
  коммитится — ~60МБ) и путь пишется в `products.photo_path`. Один файл на артикул,
  даже если в прайсе фото повторяется на каждый размер
- `/отчёт`, `/размеры [артикул]`, `/клиенты`, `/abc [7|30|90]`, `/аутсайдеры [7|30|90]`,
  `/сток [артикул]`, `/маржа [7|30|90]`, `/связки` — все работают на реальных данных
- Приём свободного текста от продавцов → Claude API → `demand_signals`
- **X2POS API (v1.6)** — `shared/x2pos_api.php`, кнопка «🔄 Синк с X2POS» / `/синк_x2pos`:
  подтягивает товары, категории, остатки, клиентов, платежи и себестоимость
  (из последней завершённой приёмки — этого не было ни в одной файловой
  выгрузке) напрямую с сервера, без ручной загрузки файлов. У API **нет**
  метода чтения истории продаж (только `POST /api/orders` для создания) —
  продажи по-прежнему загружаются файлом «История продаж по товарам».
  Инкрементально: каждый следующий синк тянет только изменения после
  прошлого (`changed_after` из `sync_log`). Артикул берётся из `vendor_code`
  разновидности (совместимо с историей продаж, ключующейся по тем же
  строковым артикулам — не по числовым `product_id`/`variation_id` из API)

Все 5 типов X2POS-выгрузок из раздела 2.2 ТЗ теперь распознаются и импортируются.

⚠️ **X2POS отдаёт продажи двумя разными файлами**: «Экспорт продаж» — только
итог чека (сумма, скидка, контрагент), без товаров; «История продаж по товарам» —
построчный состав (то, что нужно для ABC/XYZ, `/сток`, `/маржа`, `/связки`). Оба
импортированы и используются по назначению — чек для привязки клиента/LTV,
построчный файл для товарной аналитики.

Не готово (нужны доп. данные/решения):
- `/тренд` — данные для графика в `sales` уже есть, не реализована отправка изображения
  через QuickChart.io (раздел 4 ТЗ, шаг 10 плана)
- Реконсиляция платежей с эквайринг-комиссией — данные есть в `payments.purpose`
  (напр. «Комиссия банка 0.95 %»), но парсинг/сверка не реализованы (раздел 2.2 ТЗ:
  не первый приоритет)
- Kaspi API интеграция (`/обновить`) — нужен рабочий токен для первого реального запроса
- Проактивные алерты (таблица `alerts`, раздел 4) — данные для порогов теперь есть,
  сама таблица и дедупликация уведомлений не реализованы
- Сравнение цен конкурентов (раздел 2.4)
- Пороги ABC/XYZ (0.10/0.25 коэфф. вариации) и другие калиброваны по разумным
  умолчаниям — раздел 10 ТЗ прямо говорит, что их нужно калибровать по факту
  первого месяца реальных данных

## Безопасность

`shared/config.php` в `.gitignore` — не коммитить, создаётся на сервере вручную.
`.htaccess` с `Deny from all` уже лежит в `shared/`, `db/` и `scripts/` — блокирует
прямой доступ по URL к конфигу, файлу SQLite и CLI-скрипту импорта (раздел 7 ТЗ).
